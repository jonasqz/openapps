Die acht Faelle
---------------
1. App mit Router und Freigabe
   GET https://app1.local.test/            -> 200
   In der App angekommen (Body der Dummy-App):
     X-Auth-User-Id: usr_stub_1
     X-Auth-User-Email: stub@example.invalid
     X-Auth-Groups: team-a,team-b
     X-Auth-Issued-At: 0
     X-Auth-Signature: stub-signature-not-a-real-hmac
   Alle fuenf aus Spec 3.1, keiner mehr.                            OK

2. Forward-Auth sagt 403
   GET https://app1.local.test/deny        -> 403
   Body: "stub: keine Freigabe". Kein App-Inhalt, kein "app":-Feld,
   kein Set-Cookie. Die App wurde nicht erreicht.                   OK

3. Keine Session
   GET https://app1.local.test/nosession   -> 302
   location: https://control-plane.local.test/login
             ?next=https://app1.local.test/nosession
   Traefik gibt das 3xx der Control Plane an den Client weiter.      OK

4. Client schickt die Identitaets-Header selbst
   GET https://app1.local.test/ mit
     X-Auth-User-Id: admin, X-Auth-User-Email: eve@example.invalid,
     X-Auth-Groups: admins, X-Auth-Issued-At: 9999999999,
     X-Auth-Signature: gefaelscht
   -> 200, aber in der App steht:
     X-Auth-User-Id: usr_stub_1 (nicht admin)
     X-Auth-Groups: team-a,team-b (nicht admins)
     X-Auth-Signature: stub-signature-not-a-real-hmac (nicht gefaelscht)
     X-Auth-Issued-At: 0 (nicht 9999999999)
   Null gefaelschte Werte in der App. Das ist der Angriff aus ADR 0004,
   und die Strip-Middleware am Entrypoint haelt ihn.                OK

5. Domain ohne Router
   GET https://unbekannt.local.test/       -> 403
   server: openapps-forward-auth-stub, Body "stub: keine App fuer diese
   Domain" — abgelehnt von der Control Plane (Schritt 1 der Pruefkette),
   bevor der Catch-all zum Zug kommt. Beide Schichten liegen auf dem Weg.  OK

5b. Dieselbe Domain, Forward-Auth sagt absichtlich 200
   GET https://unbekannt.local.test/force-allow -> 403
   server: nginx, x-openapps-deny: catch-all,
   Body "403 Diese Domain ist nicht freigegeben."
   Also: Selbst wenn die Auth irrt, sperrt der Catch-all. Nur so ist
   belegt, dass das Deny-Backend wirklich antwortet und nicht nur
   dasteht.                                                          OK

6. Labels weggenommen (der Coolify-Update-Fall)
   a) Container ohne Labels, Domain im Stub als freigegeben eingetragen:
      GET https://nolabels.local.test/     -> 403, x-openapps-deny: catch-all
   b) Echte Wegnahme an einer laufenden App: app2 vorher 200, dann
      `docker rm -f` und als Container ohne Traefik-Labels neu gestartet:
      GET https://app2.local.test/         -> 403, server: nginx,
      x-openapps-deny: catch-all
      /api/http/routers zeigt openapps-app2@docker nicht mehr.
   Kein 200, kein App-Inhalt. Die App ist unerreichbar, nie ungeschuetzt. OK

7. Control Plane gestoppt (`docker compose stop control-plane`)
   https://app1.local.test/       -> 502
   https://app2.local.test/       -> 502
   https://unbekannt.local.test/  -> 502
   Fuer alle Domains dasselbe: kein Durchlass. Kein Fall, in dem der
   Ausfall der Control Plane eine App oeffnet.                        OK

8. Control Plane langsam (Stub schlaeft 3,5 s)
   GET https://app1.local.test/slow -> 504 nach 2 s
   Abbruch am 2-s-Transport, App nicht erreicht.                      OK

   Wichtig zur Herkunft dieser Zeile: Beim ersten Lauf fiel genau dieser
   Fall. `forwardAuth` benutzt den Standard-`serversTransport` **nicht**;
   ihr HTTP-Client hat 30 s fest eingebaut. Ergebnis damals:
   "app1 /slow -> 200 nach 7s". Die Konfiguration war falsch, nicht der
   Test. Behoben ueber den internen `authz`-Entrypoint plus
   serversTransport `openapps-fast-fail`
   (infra/traefik/dynamic/control-plane.yml).
